# Linear OLS FPGA literature review — five-paper comparison

Research date: 2 October 2026. Five distinct primary papers now have verified OLS implementations, resource results and reported performance evidence. Timing evidence varies: Ferreira reports a one-cycle implementation claim without a clock frequency; Royer estimates Fmax; Van Court uses post-place-and-route simulation. These are not five identical weather-inference systems or five board-measured benchmarks.

## Scope of comparison

Our [speed specification](linear_ols_speed_optimized_spec.md) trains three coefficients offline in C++; FPGA inference evaluates two weighted temperature differences, a diurnal anchor, and a bias. Its 50 MHz, II=1, latency ≤8 cycles and two embedded multipliers are targets, not measured results. The [resource specification](linear_ols_resource_optimized_spec.md) targets one shared multiplier and II/latency ≤10 cycles. Neither specification implements OLS fitting on FPGA.

Do not equate a least-squares solver's matrix solution time with inference latency. FPGA slices, LUTs, Cyclone II LEs, and DSP blocks are different hardware units. Report numeric format, problem size, circuit boundary, and timing evidence before interpreting comparisons. A linear model alone does not prove OLS training; gradient-descent LR is separately labelled.

## Specification example to learn from

Royer et al. provide a detailed implementation description (§IV.A–F), although not a standalone normative RTL specification. Input arrives on two sample ports with sequence-start and length controls; blocks have 128 or 256 samples. Accumulators feed a second FSM while the next block starts. Constants occupy the 18-bit multiplier input and accumulated data the 25-bit input. The coefficient stage lasts five cycles. Table I defines scaled ROM constants; §IV.D–E explains alignment, truncation, and output precision.

Use this as a pattern for documenting interface, scheduling, constants, bit widths and numerical error. Its values cannot be copied into our temperature model. It supplies implementation specification details to learn from; a standalone normative spec was not explicitly required by the user. Complete cycle-by-cycle reset/handshake semantics are not supplied, so it is not a drop-in RTL contract.

## Explicit design-document audit (supplementary)

[AccelReg](https://www.cs.columbia.edu/~sedwards/classes/2025/4840-spring/designs/AccelReg.pdf), PDF pp. 4–6, specifies 32-bit input/output registers, register-address selectors, start/reset control and Avalon/driver communication. Hardware calculates sums and numerators; software performs final floating-point division. This is a useful interface-specification example, but not a verified paper with synthesis results.

There is a substantive typo on PDF p. 3: prose gives denominator `S1*S3-S2*S2`, but its defined sums and displayed coefficient equation require `S1*S4-S2*S2` (n·Σx²−(Σx)²). The later output register definition on p. 4 agrees with the corrected denominator. Do not copy the inconsistent expression. Overflow widths and exact cycle/reset semantics also need a stronger contract before implementing its design.

## Additional primary-source audit

### CMS three-parameter OLS fitter

Navarro-Tobar and León Holgado's [updated TWEPP 2024 presentation](https://indico.cern.ch/event/1381495/contributions/5988787/attachments/2938319/5638160/TWEPP24_Alvaro_Navarro.pdf), **PDF p. 9**, explicitly defines ordinary least squares: `b=(XᵀX)⁻¹Xᵀy`, with three output parameters (collision time, position, slope). It precomputes the pseudoinverse-like matrix C offline and stores it in ROM; FPGA arithmetic computes `b=C*y`. This is a useful constant-coefficient datapath comparison, but its constants come from detector geometry rather than training a weather predictor.

The eight-layer fitter reports **3000 LUTs, 4500 FFs, 20 BRAMs, 25 DSPs, and 15-clock latency**. One-superlayer constants occupy approximately 50 rows × 200 bits in distributed RAM; two-superlayer constants approximately 1500 rows × 360 bits, using 20 BRAMs. PDF p. 14 reports **480 MHz** and **0.5 μs** latency for the overall trigger implementation, whose resources are approximately 350000 LUTs, 500000 FFs, 1000 BRAMs, 150 URAMs and 850 DSPs. The system figures must not be assigned to the isolated OLS fitter. Nor does the slide supply a standalone fitter Fmax measurement. The earlier [conference abstract](https://indico.cern.ch/event/1381495/contributions/5988787/) describes 480 MHz as a design goal and integration critical paths near 3 ns; the updated presentation states 480 MHz in its final remarks. Preserve this source/version distinction rather than silently merging timing claims.

The corresponding JINST DOI is a full-text retrieval lead; its publisher PDF returned an access error. These are **verified primary slide results**, not counted as an additional verified full-paper benchmark. Page 9 was visually inspected to confirm the equation and numeric labels.

### Pipelining versus time multiplexing in OLS

Garrido and Grajal, **Continuous-flow variable-length memoryless linear regression architecture** (Electronics Letters 2013), DOI 10.1049/el.2013.2106, [university postprint](https://liu.diva-portal.org/smash/get/diva2:692306/FULLTEXT01.pdf), PDF pp. 2–3. It minimizes MSE to fit slope/intercept and additionally returns fit MSE. It does not have three learned coefficients: MSE is an output statistic.

PDF p. 3, Table 2 compares fully pipelined / time-multiplexed component counts: **12 / 7 adders, 13 / 4 multipliers, 3 / 1 dividers, 6 / 18 registers**. These are architecture components, not synthesized LUT/FF/DSP counts. It describes one input sample per clock and overlap between accumulation and result calculation, provided the time-multiplexed version's block length is large enough. No named FPGA device, numeric clock frequency, measured latency, or utilization table appears in the three-page postprint. Therefore it is an excellent architecture explanation for our speed/resource tradeoff, but **not counted as a measured FPGA benchmark**.

## Additional implementation specification to learn from: Ferreira 2019

PDF p. 3 Algorithm 1 and p. 4 Figure 4 define a regression entity with `start`, eight 32-bit x inputs and eight 32-bit y inputs, returning two 32-bit coefficients. A separate prediction entity takes `start`, x and both coefficients, returning a 32-bit prediction. PDF p. 3 describes a signed 32-bit representation with 16 fractional bits and 15 integer bits in addition to sign. The 2×2 inverse uses a three-iteration Newton–Raphson reciprocal approximation; zero or near-zero determinant handling is not specified.

The pseudocode uses `rising_edge(start)` and the block diagram does not expose an independent clock. Treat the paper’s single-cycle statement as an author-reported implementation claim, not a validated timing contract to copy. Reset, valid/ready semantics, overflow/rounding rules and achieved clock frequency are insufficiently specified for a drop-in RTL implementation. Our specs should retain explicit clock/reset, accepted-sample semantics and bit-exact arithmetic.
